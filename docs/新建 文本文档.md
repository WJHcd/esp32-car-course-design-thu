## 为什么 11% 在这辆车上特别容易“不走”

运动学输出在 [walking.c](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/walking.c:364) 中为：

```c
A = -forward + turn + strafe
C = +forward + turn + strafe
B = -turn * 0.68 + ...
```

而 C 轮还有一个已经实车标定的 `0.90` 系数：

```c
static const float s_motor_gain[MOTOR_NUM] = {
    1.00f, 1.00f, 0.90f
};
```

所以在球完全居中、转向修正为 0 时，`APPROACH_SPEED = 11%` 最终约为：

| 电机 | 实际指令 |
|---|---:|
| A 前轮 | -11.0% |
| C 前轮 | +9.9% |
| B 后轮 | 0% |

项目参数自己的注释已经指出，约 `9%` 是低速物理下限。换句话说，C 轮的 9.9% 只是勉强碰到死区上沿；车体负载、地毯或地面摩擦、电池电压、球顶住车头、轮子安装松紧稍有变化，就可能起不来。

如果球偏离中心，问题更明显。当前：

```c
turn = (int)(off * 8.0f);
```

最大大约会产生 ±4% 的转向修正。例如球在画面一侧时，两个前轮可能变成：

```text
A：约 15%
C：约 6.3%
```

或反过来：

```text
A：约 7%
C：约 13.5%
```

此时一侧轮子直接落入死区。结果就不是平滑地朝球转，而是：

- 一只轮子能动，另一只轮子不动；
- 车体轻微别住；
- PWM 指令一直存在，但车辆没有实际位移；
- 人手轻推一下克服静摩擦后，车马上又能继续。

这和你之前遇到的“轻轻推一下马上恢复”是同一种机制。

## “车—球—终点已经在一条直线上”为什么仍可能停着

目前的状态机不仅要求三点共线，还要求球和绿色终点组成的目标对位于画面中间。逻辑在 [ball_task.c](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/ball_task.c:450)：

```c
e = ball_x - marker_x;
pair_x = 0.5 * (ball_x + marker_x);
pair_off = pair_x - 0.5;
```

只有同时满足：

```c
fabs(e) <= 0.06
fabs(pair_off) <= 0.08
```

才会进入 `PUSH`。

也就是说：

- `e` 很小：球和绿色终点在同一条视觉直线上；
- `pair_off` 很小：这条直线还必须位于画面中央。

如果车、球、终点确实共线，但是整条线在画面左侧或右侧，程序不会向前推，而是先执行原地“踢转”，试图把目标对带回画面中央。这种策略本身有道理，因为如果目标线不在车头中心，直接前进可能擦到球的一侧。

问题在于，当前踢转力量不足。

## 对准时的“踢转”太弱，尤其是后轮 B

参数在 [ball_task.h](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/ball_task.h:79)：

```c
#define BALL_ALIGN_KICK_TURN_PCT  13
#define BALL_ALIGN_KICK_MIN_MS    25u
```

纯旋转时三个轮子的实际输出大约是：

| 电机 | 实际指令 |
|---|---:|
| A | +13.0% |
| C | +11.7% |
| B | -8.84% |

其中 B 轮因为 `TURN_B_GAIN = 0.68`，最终只有约 `8.84%`，就在死区附近甚至低于有效起转值。

同时最短脉冲只有 25ms。25ms 对软件来说执行了一个动作，但对带负载的机械底盘来说，很可能只是电流刚建立，车轮还没克服静摩擦，脉冲就结束了。

于是程序看到的逻辑是：

```text
发出 25~几十毫秒转向指令
→ 停车
→ 等待下一帧
→ 再发一个很短的指令
→ 再停车
```

而实车看到的现象是：

```text
电机可能轻微响一下
→ 车基本不动
→ 长时间停着
→ 偶尔抖一下
```

::code-comment{title="[P1] 对准踢转不足以可靠克服静摩擦" body="BALL_ALIGN_KICK_TURN_PCT=13 时，后轮 B 经过 TURN_B_GAIN=0.68 后只有约 8.84%，而最短脉冲仅 25ms。这很可能不足以让后轮从静止起转，导致软件不断执行“踢一脚—等一帧”，实车却基本不动。建议仅在球任务的 ALIGN 状态提高踢转档位和最短持续时间，不要恢复全局低速补偿。" file="D:/Mycar-ir-style-scan/Code/task2-camera-line/main/ball_task.h" start=79 end=83 priority=1}

## TFT 显示把视觉反馈周期拉到了约 3 fps

当前 TFT SPI 时钟仍然是 1MHz：

```c
#define TFT_SPI_CLOCK_HZ (1 * 1000 * 1000)
```

见 [tft_st7735.c](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/tft_st7735.c:14)。

一帧 128×160、RGB565 画面大约需要传输：

```text
128 × 160 × 2 = 40960 字节
```

1MHz 下，仅理论像素传输时间就约为：

```text
40960 × 8 / 1,000,000 ≈ 0.328 秒
```

还没有计算大量 60 字节分块、SPI 事务切换和绘制开销。

更关键的是，当前显示回调是在摄像头处理任务内部同步调用的：

```c
s_frame_cb(rgb_buf, jpeg_out.width, jpeg_out.height);
```

见 [camera_line.c](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/camera_line.c:486)。

也就是说，在 TFT 整帧传输完成之前，摄像头处理任务不能完成这一帧，也不能开始处理下一帧。这正是 [main.c](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/main.c:290) 中直接写着“约 3fps”的原因。

3 fps 不是小车完全不走的首要原因，但它严重放大了对准脉冲的问题：

- 发出最短 25ms 的踢转；
- 剩余约 300ms 停车等待下一帧；
- 实际动作占空比可能不到 10%；
- 如果这 25ms 又不足以克服静摩擦，就会持续原地不动。

所以现在不是单纯“摄像头识别慢”，而是“低帧率反馈 + 过短低速脉冲”的组合问题。

## 程序还有一些“主动停车”的路径

当前代码中以下停车是有意设计的，因此从外观上容易和电机卡死混淆：

| 状态 | 主动停车原因 |
|---|---|
| `GIMBAL_UP` | 等云台到位 |
| `SURVEY` 前 2 秒 | 静止等待识别红球/蓝球 |

| `ALIGN` 没看到球 | 立即停车，不允许盲转 |
| `PUSH` 判断球接近终点 | 停车等待第二帧确认 |
| `DONE` | 两球完成、单球超时放弃或总任务超时后永久停车 |

其中最容易造成误判的是 `PUSH` 的到位检测。

当前只要球框中心与绿色角标中心满足：


```c
walking_direct_command(0, 0, 0);
```

见 [ball_task.c](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/ball_task.c:568)。

如果透视角度、球框大小或绿色区域框的位置导致两个中心在图像上提前接近，程序就可能在球尚未真正推进绿色区域时提前刹停。因为车一停，图像几何关系通常仍然满足条件，下一帧便会把这个球标记为“已完成”。

因此：

- “车、球、终点在一条线上”本身不会触发停车；
- 但如果球和绿色终点的图像中心也已经比较接近，就可能触发“静止确认”；
- 用户看到的就是：框都识别出来了，方向也对，但车突然不走了。

## 当前所谓“防卡死”其实不能检测小车是否真的在动

`TASK2_MODE 8` 中只初始化了：

```c
gimbal_init();
walking_init();
walking_set_output_enabled(true);
```

没有初始化或使用编码器，见 [main.c](D:/Mycar-ir-style-scan/Code/task2-camera-line/main/main.c:277)。

`ball_task` 也没有读取实际转速。程序只能知道“我下发了 11%”，但不知道：

- A 轮有没有转；
- C 轮有没有转；
- B 轮是否卡在死区；
- 车体有没有实际移动；
- 球是不是卡在车头。

甚至 `s_push_drive_ms` 只是每次下发推进指令就固定加 20ms：

```c
s_push_drive_ms += BALL_CTRL_PERIOD_MS;
```

它累计的是“软件认为自己推了多久”，不是实际运动时间或距离。即使三个轮子都没有动，这个数仍然增长。

因此当前的“防卡死”主要是：

- 某个状态超时后退出；
- 球丢失后倒车或重新找；
- 推球超过 15 秒后放弃；

它不能解决真正的电机静摩擦卡死。

## 还有一个 RETURN 状态的确定性逻辑错误

球在车头滑出画面后，代码原本想只倒车 400ms：

```c
s_return_ms = BALL_REALIGN_BACKUP_MS;
set_state(BALL_TASK_RETURN, now_ms);
```

但进入 `set_state(BALL_TASK_RETURN)` 后，`s_return_ms` 会立即被重新计算：

```c
s_return_ms = s_push_drive_ms * BALL_RETURN_TIME_SCALE;
```

也就是说，前面指定的 400ms 被覆盖了。实际倒车时长可能远大于或小于期望值。

这不会直接解释最初的“不起步”，但会导致球丢失恢复后位置不可控，进而让下一轮球—车—终点关系变差。

## 推荐的修改方向

我建议下一版按以下顺序修复，而且不要重新加入电机驱动层的全局低速补偿。你们已经实测证明，全局补偿会造成正常巡线左右摇摆；这次应该只在找球/推球任务局部处理。

1. 修正 `APPROACH` 助推调用。

把固定的：

```c
walking_direct_command(BALL_APPROACH_SPEED_PCT, turn, 0);
```

改为真正使用：

```c
walking_direct_command(push_speed_now(now_ms), turn, 0);
```

这样进入接近状态后会先以 20% 启动 350ms，再用 600ms 平滑下降。这个功能已经写好，只是当前忘了调用。

2. 将接近巡航速度从 11% 提到约 12%～13%。

11% 在 C 轮上只有 9.9%，留给负载变化的余量太小。巡航不必提得很高，关键是让两个前轮都稳定越过静摩擦区。为了防止偏转时一侧跌进死区，还应限制低速下的最大 `turn`，或者在球任务内部保证需要转动的轮子不低于局部最小有效值。

3. 对准踢转改为任务局部的可靠启动档。

建议初始范围：

```c
BALL_ALIGN_KICK_TURN_PCT = 15～16
BALL_ALIGN_KICK_MIN_MS   = 80～120ms
```

当 `turn=15` 时，B 轮约为：

```text
15 × 0.68 = 10.2%
```

至少明显越过当前注释中的 9% 物理下限。这个补偿只用于 `BALL_TASK_ALIGN`，不会影响巡线。

4. 保留“踢一下—看一帧”，但解决 3fps 的长时间空档。

更合适的结构是：

```text
收到新帧
→ 计算动作
→ 以足够的速度执行 80～200ms
→ 停稳
→ 等下一帧
```

而不是当前的 25ms 弱脉冲。进一步可以把 TFT 显示从摄像头处理任务里解耦，使用独立低优先级显示任务，只显示最新的一帧；或者在接线稳定的情况下把 TFT SPI 从 1MHz 提高到更合理的频率。这样视觉控制不必被整屏刷新阻塞。

5. 给红球、蓝球分别锁定绿色终点。

建议在进入 `ALIGN` 时：

```text
选择一个绿色终点
→ 记录它的位置/轨迹
→ ALIGN 和 PUSH 阶段持续跟踪同一个终点
→ 只有连续若干帧丢失才允许重新选择
```

至于红球固定对应左终点、蓝球固定对应右终点，还是两球都允许去任意尚未占用的绿色终点，需要按实际赛道规则决定。但无论如何，都不应每帧无记忆地重新选最近框。

6. 收紧到达终点判断。

建议至少增加：

- 已进入 `PUSH` 并实际推进超过约 600～1000ms；
- 球和终点连续 2～3 个新帧满足条件；
- 连续帧之间距离总体在减小；
- 候选第一帧不要立即永久刹停，可以低速保持或短暂停稳后复核；
- 有编码器时，再要求推进期间确实检测到了轮子转动。

7. 加一个球任务专用的编码器防卡死，而不是全局抬高 PWM。

逻辑可以是：

```text
下发非零运动指令超过 200～300ms
→ 对应轮子转速仍接近 0
→ 执行一次 18%～20%、持续 150～250ms 的局部脱困助推
→ 平滑回到巡航速度
→ 连续重试仍不动才停车并打印故障
```

这样能直接处理“手推一下就恢复”的物理静摩擦问题，又不会让正常摄像头巡线一直受到低速补偿而左右摇摆。

8. 增强调试日志。

当前串口只打印识别框和状态，例如 `state=APPROACH`，但不打印实际运动命令。建议增加：

```text
state
forward / turn / strafe
A / B / C 最终 PWM
```
